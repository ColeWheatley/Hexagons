Glossary — terms used below
Manifest (tile_manifest.json)
A ~95 KB JSON "table of contents": lists every terrain island and every texture page with its bounds and sizes. It's the first thing the app downloads; nothing renders without it.
Gosper island / geometry binaries (gosper_*.bin)
The unit of terrain. One island = a snowflake-shaped cluster of 16,807 small hexes (6.4 m each), stored as one ~280 KB binary file holding elevations and slopes. The current map is 197 islands around Stubai. "Matching binaries" in the Codex audit meant: the manifest lists 197 of these files but zero existed on disk — the checkout's data was from an older format.
Texture pages & tiers
The aerial photography, cut into 1024 m squares ("pages"), each baked at three resolutions ("tiers"): low 128 px, medium 256 px, high 4096 px. Stored as KTX2 files — a GPU-compressed image format that stays compressed in video memory, so a high page costs ~7 MB of VRAM instead of ~67 MB.
Basis transcoder
A WebAssembly decoder (~a few MB of memory per copy) that converts KTX2 files into whatever compressed format the user's specific GPU speaks. Runs inside the worker threads.
Worker pool ("round-robin workers")
2–6 background browser threads that parse geometry binaries and decode textures so the main thread doesn't stutter. "Round-robin" just means jobs are dealt to them in turn — and currently each one may load its own copy of the Basis decoder.
Residency / VRAM ledger
"Residency" = which texture pages are currently held in memory. The VRAM ledger (vram_ledger.js) is the app's own bookkeeping of GPU memory use; the high tier has a 256 MB budget with least-recently-used eviction.
The peaks GeoJSON
Yes — assets/tirol_peaks.geojson is the file with the peak names: 4,368 Tirol summits with name, elevation, prominence. It's 1.73 MB and is parsed on the main thread the first time you click the search box.
DPR (devicePixelRatio)
How many physical pixels per CSS pixel. A retina laptop is 2, phones up to 3+. Rendering at DPR 3 costs ~9× the pixels of DPR 1. The app currently renders at full native DPR, uncapped.
Render-on-demand
The animation loop runs every frame but skips actually drawing when nothing changed. Saves battery — and is why the FPS readout "drops to 2–4" when idle: the counter divides rendered frames by wall-clock time.
Sintered / engine states
The app's activity ladder: MOVING (camera in motion) → SINTERING (just stopped, upgrading quality) → STATIC (settled, renders only on demand).
TTFTF
Time To First Textured Frame — from page open until the visible terrain is fully painted with real imagery. The single best first-impression metric.
Diagnostic tattoos
Colored watermarks the baker stamps onto texture tiers in dev bakes (green=low, blue=medium, pink=high) so you can see which tier is on screen. The live beta currently shows them to the public.

FrontendGain: very high (reliability)🔵 StandardIntegrated; live fault-injection gate remains

Right now, a failed terrain download silently never appears (no retry); a failed manifest leaves the loading screen spinning forever; and if the GPU resets (which happens — laptops on battery, driver hiccups, memory pressure) the app goes permanently blank because nothing listens for the "context restored" event. Add: bounded retries with increasing delays for every network fetch, an explicit user-visible error state with a Retry button instead of an infinite spinner, a rebuild path after GPU context loss, and a friendly "this device isn't supported" screen instead of a silent console exception.

Done when: under a fault-injection proxy that drops 10% of requests, all terrain eventually appears; a forced GPU context loss recovers within 5 s; no failure leaves the spinner up more than 10 s; no resource is retried more than 3 times.

Frontend + backendGain: very high (first impression)✓ Verified: median TTFTF 237 ms, 57% faster

Cole's idea. First load is network-bound, and for photographic imagery a small WebP is a fraction of the bytes of the equivalent KTX2 file at similar perceptual quality — plus the browser decodes WebP off-thread for free, no WASM transcoder in the critical path. Add a fourth, deliberately transient tier: a tiny WebP per page fetched first so terrain is painted almost immediately, then lazily replaced by the proper compressed low tier when the network is quiet, at which point the WebP version is released. The catch that makes this frontier-grade: a decoded WebP sits in GPU memory uncompressed (~15× more bytes per pixel than the compressed tiers), so the VRAM ledger must track the interim pages and the lazy replacement is mandatory correctness, not polish.

Done when: cold-cache TTFTF improves ≥25% (3 runs, median), steady-state VRAM is unchanged, and total first-session bytes rise by no more than the low tier's size.
FrontendGain: very high (bytes + VRAM)✓ Verified: demand-driven residency + 7.3 MB orbit ledger peak

The live beta downloads all 149 low-resolution and all 149 medium-resolution texture pages up front — the entire map's imagery — regardless of where the camera is pointing. On the current Stubai square that's tolerable; for the larger selected production region it will not be. Make low/medium residency demand-driven like the high tier already is: keep pages that are visible, a guard ring around the view, and a small predictive set — nothing else before idle. Compounds directly with AA-4: demand-driven + bootstrap WebP is the complete first-load story.

Done when: no off-screen page is requested before idle; cold-load bytes and peak VRAM drop; scripted orbit/traverse flights show zero visibly-blank pages.
Frontend + deployGain: very high (startup)✓ Bundled, self-hosted, hashed, precompressed

Startup currently pays for: ~15 separate unminified JavaScript module requests (the main file alone is 169 KB raw, ~45 KB gzipped); the Three.js 3D library fetched from a third-party CDN (unpkg — extra connection, and their outage is your outage); a Google font that blocks rendering; and a completely dead touch library (hammer.min.js) that is loaded and referenced nowhere. Also: geometry binaries, the manifest, and the 1.73 MB peaks file are served uncompressed (the manifest gzips 94.7→13.3 KB). Done when: app reaches ready with all third-party domains blocked; requests before first render drop from ~15 to ~3; transfer bytes drop ≥40%; benchmark FPS unregressed.
FrontendGain: high (returning users)Service-worker control/cache pass; localhost warm gain 4.1% fails the 60% gate

Nothing is cached across visits today — the page shell and manifest are explicitly marked "never store," so every visit re-pays most of the startup cost. Since every large asset URL already carries a version key that changes when data is rebaked, a cache-first service worker for geometry, textures, and bundled code is safe and mechanical. Note this is not the "offline mountain mode" product feature (that's H-3, a real decision about storage budgets and consent) — this is just standard browser caching done right.

Done when: second visit fetches only the manifest; warm reload TTFTF improves ≥60%; a rebake with new version keys invalidates cleanly.
FrontendGain: high (battery, background CPU)✓ Live gate: settled/hidden 0 ticks, 0 renders

Even when the map is completely settled, the animation loop wakes up 60× per second and does real work — queue maintenance, camera math, culling checks, profiler feeding — before deciding "nothing changed" and skipping the draw. And it keeps doing all of it when the tab is hidden (there's no visibility handling at all). Restructure to event-driven waking: input, resize, a worker finishing, or a settle timer wakes the scheduler; a hidden tab pauses it entirely. This also relates to the KNOWN_BUGS question of whether "sintered mode" is wasting battery — after this change, the answer is provably no.

Done when: after 2 s settled: zero renders and ≤1 scheduler callback/second; input wakes within one frame; hidden-tab CPU is ~0%; loading still progresses normally.
FrontendGain: high (memory + first texture)✓ Dedicated lanes, ≤2 decoders, cancellable queued work

The 2–6 background worker threads treat geometry parsing and texture decoding as interchangeable jobs dealt out in turn. Two consequences: each worker may end up loading its own multi-megabyte copy of the Basis texture decoder, and after a fast pan a burst of geometry jobs can starve texture decoding — terrain appears but stays unpainted. Dedicate one or two workers to textures with a single pre-warmed decoder, keep the rest for geometry, and let stale jobs from an abandoned view be cancelled rather than completed (view epochs / abortable jobs).

Done when: at most two decoder instances exist; peak JS heap drops measurably; under throttled load, first textured terrain improves ≥20%; a rapid pan cancels the previous view's queued jobs.
FrontendGain: high (FPS on retina/phones)Code integratedHuman DPR-2 visual comparison remains

The renderer draws at the display's full native pixel density, uncapped — on a 3× phone that's ~9× the pixels of 1×, mostly invisible on photographic terrain — and never re-checks when the window moves between monitors. Separately, preserveDrawingBuffer: true (which keeps every rendered frame around so screenshots work) is on for all users all the time; it costs memory and performance and is only needed by the benchmark's screenshot capture. Cap DPR at 2 (optionally dropping to 1.5 while the camera is moving), re-apply on resize, and enable the screenshot flag only under ?bench. While touching the GPU setup, share the identical cap/skirt BufferAttribute objects and avoid throwaway per-mesh instance buffers instead of uploading the same static geometry repeatedly.

Done when: frame-time p95 improves on a DPR>2 profile; bench screenshots still work; a screenshot diff at DPR 2 vs native shows no meaningful quality loss; cap/skirt meshes reference the same static attributes and GPU buffer/upload counts fall with geometry parity.
FrontendGain: high (low-end devices)Code/matrix contracts integrated; real device matrix remains
